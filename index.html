The gap

Remediation stops at the inbox. The threat doesn't.

Email security tools are good at catching a malicious message and pulling it — after delivery, once they've changed their mind. But delivery is also when a message multiplies. By the time the verdict flips, copies are sitting in systems the security tool has no reach into.

Those copies keep the old disposition. The backup restores a live threat. The archive hands it to an auditor. The AI assistant retrieves it as a trusted source. Nobody told them the verdict changed — because nothing was built to.

Why guard

The backup doesn't just store the threat. It puts it back.

Every other copy sits still. This one comes back. A restore is the one system that re-delivers a message into the live mailbox — unread, clickable, and carrying the verdict it had before anyone changed their mind.

The sequence is ordinary, which is what makes it dangerous. An attacker seeds phishing over weeks. Some of it is caught and pulled. Later they land something real — bad enough that the mailbox gets restored from backup, or a retention hold reaches back into the archive. That snapshot was taken before the cleanup. So the restore faithfully returns every malicious message the security tool had already removed.

The remediation is undone. Nothing alerts, because nothing was built to watch the restore path — the backup is doing exactly what it was bought to do. The user opens a message they were already protected from, delivered this time by the recovery tool.

With Cascade

Auto-cleared

Cascade detects the restore, re-checks what came back against every verdict it holds, and removes what shouldn't have returned — then records it.

You can't fix this inside the backup. Backups are immutable on purpose — that immutability is the product. Reaching in to delete a message would break the guarantee the backup exists to make, and most platforms won't permit it at the item level anyway.

So Cascade doesn't fight the backup. It guards the door the backup opens — watching the restore path, re-evaluating what re-enters against the current verdict, and acting on what shouldn't have come back.

Source-agnostic by design — whichever tool produced the original verdict, the returning copy is matched against everything Cascade holds. And verdicts move: a message that was clean when it was backed up can be known-bad by the time it's restored. That one is caught on the way in too.

The approach

A control plane for the changed verdict.

Cascade is vendor-neutral. It takes a verdict from whatever security stack produced it, finds every place the message went, applies the strongest action each of those systems will accept, holds the line against the ones that put it back — and records what it did.

  1. 01 / Map

    Find every copy

    Trace the message across mail, backup, archive, ticketing, file stores, and indexes — by identity, not by keyword.

  2. 02 / Propagate

    Carry the verdict

    Apply the strongest action each system accepts — remove, restrict, tag, or flag — reversibly, never destructively.

  3. 03 / Guard

    Hold the line

    Watch the paths that put messages back — restores, archive recoveries, re-syncs — and re-check what returns against the current verdict. Cleanup is a moment. This doesn't stop.

  4. 04 / Prove

    Show your work

    Produce a disposition record: what was found, what was done, and where — an answer for the audit, not a guess.

Cascade sources verdicts. It never invents them. The detection call stays with the security stack you already bought — Cascade makes that call reach the places it couldn't, and keeps it enforced as systems hand copies back.
